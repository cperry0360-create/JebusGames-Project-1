# The ring, and the two backdrops

**2026-09-02**

Two pieces of work: the backdrops got the WebP treatment the map plate got, and
the radial ring was built and swapped in. `BuildMenu`, `TowerPanel` and
`TowerIcon` are deleted.

---

## 1. The backdrops

Both 1920×1080, both colour type 2 — **no alpha channel at all**, so there is
nothing lossy encoding can lose that the format was carrying.

| | before | after | change |
|---|---|---|---|
| `ui/title_bg` | 2.56 MB PNG | **0.28 MB WebP q90** | −89% |
| `ui/loadout_bg` | 2.45 MB PNG | **0.29 MB WebP q90** | −88% |

WebP beat JPEG again at the same quality — 0.28 against 0.40 MB for `title_bg`,
0.29 against 0.43 for `loadout_bg`, with better PSNR in both cases (39.4 vs
38.3, 38.6 vs 37.9).

**Checked where the error actually went.** These are not the map: they are UI
art with hard black outlines and gold trim, which is exactly what a lossy codec
rings on. The worst channel error of 91 sits on the loadout lantern's rim
rather than being spread out, so three crops were magnified 1.4× — what the
backdrop is magnified by on a large display, since the design box scales up
past the 1920 source. The lantern and the helmet are indistinguishable side by
side; the amplified difference traces the outlines and nothing else. A 91 on a
black-to-bright-yellow boundary is a sub-pixel shift, not a visible one.

### Deploy weight

| | |
|---|---|
| before the map plate | 27.4 MB |
| after the map plate | 22.9 MB |
| **after the backdrops** | **18.4 MB** |

The budget passes with the image cap unchanged at 3 MB. The largest image in
the game is now the 4K map plate at 1.84 MB; the only file above it is
`music_battle.mp3` at 4.94 MB, which streams and does not block boot.

One test fix this forced, and it is the useful kind. `pngSize` asserted a PNG
signature before reading IHDR — correct until an asset changes format, at which
point it fires on a perfectly valid file and, worse, a size reader that
understands one container silently stops covering whatever moves to another. It
reads PNG, VP8, VP8L and VP8X now, and is pinned against four files of known
size so a reader returning something enormous cannot pass the containment check
it feeds.

## 2. The ring

One component — `src/ui/TowerRing.ts` — for both halves of the tower menu, with
all of its geometry in `src/systems/RingLayout.ts`.

### What it does

- A radial ring of circular icon buttons around the pad or tower. No text on a
  button: an icon, with a price badge underneath.
- HUD space, positioned by projecting the world point. **It does not scale with
  camera zoom** — a button is the same size to the thumb at every zoom, and a
  test asserts the component never reads `cam.zoom`.
- Tapping a button **buys nothing**. It opens a description panel — name, what
  the thing does, its numbers, its price. Buying needs a second, explicit press
  on that panel, on the release rather than the press, so a finger that lands
  and slides off takes the decision back.
- Tapping a different button swaps the panel without closing it. Cancel returns
  to the ring; tapping elsewhere closes everything.
- The panel is clamped so it cannot leave the screen and flips to whichever
  side has room, chosen from the room actually available rather than by a fixed
  rule.

### Build-on-empty-pad uses icons now

It was a text grid using none of the ten. Each build option carries a picture
of the tower itself, because "which one is this?" is the question a build
button has to answer and six hammers do not.

**All ten icons are placed.** `confirm` and `cancel` were unreferenced because
the confirm step did not exist; the ring's second press is that step. A test
now fails if any manifest icon is drawn nowhere.

### The tier-3 fork

Two ring buttons instead of a separate full-screen dialog — a menu inside a
menu, for the one decision in the game that cannot be undone. Each branch gets
its own description panel and its own icon, chosen from what the branch does
(`specIcon`), because two buttons wearing the same picture are a coin toss
rather than a choice.

### A locked option still opens

Two halves of one rule that pull in opposite directions. The hit area is
**exactly the plate** — a button taking presses outside its own picture steals
them from the map, and two of those side by side leave a dead strip that looks
like a bug. But the tap that *does* land on a locked option has to do
something, or the player never learns what they are saving for: it opens the
description with the shortfall on it, and only the confirm button is off.

## What the exhaustive test found

The spec asked for exhaustive, not sampled. A browser cannot do that honestly —
its synthetic taps land on buttons a thumb could never reach, which is how the
old build menu passed a reachability check while being unusable on three of
seven pads. So the placement is arithmetic in a Phaser-free module and
`tests/ringlayout.test.ts` walks **7,560 placements**: every pad, every option
count from one to six, three zooms, three viewports, notched and flat, with the
anchor at every screen edge and corner. **Position is the assertion.**

It found five real faults, four of them mine and one in the design:

1. **Square plates on a circle overlap.** The first version spaced buttons by
   arc length — a gap along the circle must be a gap between the buttons. It is
   not: two 58px squares whose centres are 65px apart at 60° have a 33px
   horizontal gap and a 56px vertical one, and overlap in both. The six-tower
   ring had four overlapping pairs.

2. **A circle does not fit the space.** The HUD leaves a wide, short strip, and
   a circle big enough to keep six plates apart is 242px in *both* directions.
   The ring is an ellipse fitted to the room available, capped at 2.2:1 before
   it stops reading as a ring.

3. **The radius floor has to yield.** A notched 844×390 leaves less height than
   the floor plus a price badge. The floor is a preference now, not a
   guarantee.

4. **Ring and panel constrain each other.** Placing one and then the other
   cannot solve a ring in the middle of a 736px strip leaving 199px either side
   for a 226px panel — everything fits, but only if the ring moves aside first.
   `fitRingAndPanel` does that, and draws a leader line back to the tower.

5. **An infinite loop.** The growth loop watched the radius caps, but `rx` is
   capped by both `rxMax` and `ry × aspect`, so it could stop growing while
   still under `rxMax`. It hung the test — a better place to find that than a
   phone.

## What only the browser found

Two things the arithmetic could not see, because the arithmetic was being given
the wrong numbers:

6. **The panel reported one height and drew another.** It was composed at full
   height and then told the geometry it was 15px shorter, so the clamp placed
   it 15px too low and the confirm and cancel buttons hung off the bottom. The
   height recorded is the height drawn now.

7. **The confirm icon was taller than its own plate** — a 40px icon on a 38px
   button. The floor is a floor; the plate grew to 46.

And one genuine squeeze: at 568×320 the panel came to 264px in a 238px space.
Fixed by cutting rather than complaining — shorter blurbs, a smaller header
badge, the panel's duplicate price moved into a named row, and the title
joining the shrink loop after the description and the stat rows. If it still
does not fit, it **says so** on the message line and in the console rather than
clipping.

## The trade-off worth knowing about

The ring may open over the **counters**. The requirement names one thing it may
never cover — the ability bar, whose buttons would fight the ring's for the
same tap — and protecting the counters as well costs 48px, which on a 568×320
screen is the difference between the description panel fitting and the game
reporting that it does not. A counter hidden while a menu is open is a fair
price; a confirm button off the bottom of the screen is not.

## Measured in the browser

Both viewports, both zoom ends, every pad, every option's description panel
opened in turn, then a real two-press purchase and the built-tower ring:

```
RESULT every button of every ring was on screen, and none overlapped another
```

- after one press on a ring button: towers 0 → 0 — it opened a description, it
  did not buy
- after confirming: towers 0 → 1 — built
- 0 off-screen buttons at 844×390 and at 568×320

Reproduce:

```sh
sh tools/harness/build.sh
sh tools/harness/run.sh ring 190 844x390
sh tools/harness/run.sh ring 190 568x320
```
