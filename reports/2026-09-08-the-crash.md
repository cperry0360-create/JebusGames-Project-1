## What the evidence actually supports

Three hypotheses have now been put to this crash. Here is where each stands.

**Browser cache — ruled out previously.** Not revisited.

**Texture memory — ruled out, and the crash report is what rules it out.** A tab
killed for memory writes no report; this one wrote a report, so JavaScript threw
and the handler caught it. The earlier session's measurement (365.6 MB peak,
cut to 231.0 MB) stands as a real and worthwhile finding — it is on this branch
and unmerged — but it is not this bug. See `reports/2026-09-07-the-crash.md`.

**Viewport — not supported by anything I can measure.** The world map and the
level-to-world-map transition were run at 844x390 with `INSETS=0,47,21,47` and
at a tablet-sized 1180x820, and the two are byte-for-byte identical:

| point | phone 844x390 + insets | tablet 1180x820 |
|---|---|---|
| after boot | 169.8 MB, 179 textures | 169.8 MB, 179 textures |
| on the world map | 231.0 MB, 218 textures | 231.0 MB, 218 textures |
| during a level | 205.3 MB, 184 textures | 205.3 MB, 184 textures |
| back on the world map | 231.0 MB, 218 textures | 231.0 MB, 218 textures |
| page errors | 0 | 0 |

Nothing throws, overflows or allocates unboundedly at the phone viewport and not
the large one. The footprint is viewport-independent, which makes sense: it is
all art plus one world-unit tiling sprite.

**So: neither.** The device pattern is real and needs an explanation, but the
explanation is not in anything the harness can see.

## The one fact that fits the device pattern, and what to do with it

The pattern any explanation must fit is: iPhone standalone crashes, iPhone tab
does not, iPad does not. One thing separates all three:

| | safe-area insets in landscape |
|---|---|
| iPhone, home-screen standalone | **non-zero** — the notch and home indicator are the app's problem |
| iPhone, Safari tab | zero — browser chrome covers them |
| iPad | zero — no notch |

Standalone on a notched iPhone is the *only* configuration in which
`safeAreaInsets()` returns anything but zeroes. That makes the inset path the
best-fitting suspect on the evidence available, so it was exercised directly:
the full `screens` audit at 844x390 with insets, and a new `standalone`
scenario with insets **and** `ANGLE=90`, which is the case that actually turns
on the housing resolution (`{"top":0,"right":47,"bottom":21,"left":47}` resolved
to `{"top":0,"right":0,"bottom":21,"left":47}`). Headless Chromium reports angle
0, so without forcing it that branch had never been exercised at all.

It came back clean: no layout faults beyond the pre-existing one, no page
errors, a playable run. **The suspect fits the pattern and does not reproduce.**

## Step 1 — making the error readable

This is the part that matters, because everything else is guesswork until the
phone sends a message and a stack.

### The script tag

`index.html` loaded `<script type="module" src="/src/main.ts">` with no
`crossorigin`. It has `crossorigin="anonymous"` now.

Being straight about this: **the bundle is same-origin with the page on Pages,
so in principle the details should already have arrived.** Module scripts are
fetched in CORS mode regardless of the attribute, and a same-origin response is
not "muted". So the attribute is insurance, not a diagnosis — it costs nothing
when the script is same-origin, and GitHub Pages answers
`Access-Control-Allow-Origin: *` so it also costs nothing if the page is ever
served from somewhere the bundle is not.

**I could not verify the Pages headers.** The sandbox cannot reach github.io;
the egress proxy answers 403 by policy. That is a claim from documentation, not
a measurement, and if the next report still says "Script error." then the
withholding is coming from somewhere other than the script tag and this line of
enquiry is finished.

### The empty STATE section

`STATE` came back empty, and that was by design rather than by accident:

```ts
export function currentState() {
  return stateProvider ? gather() : lastKnown   // before
}
```

`stateProvider` is only ever set by `GameScene`, and the crash was during boot.
So the one report anybody has of this fault could not say what the viewport was,
whether the app was standalone, what the insets were, whether the gate was up or
which scene was on screen — and every one of those was a live suspect.

`Diagnostics` now carries a context registry, and `CrashContext.ts` registers the
facts that outlive a run. It is a registry rather than a second hard-coded
provider because the interesting facts live in modules `Diagnostics` must not
import — `InputGates` imports `Diagnostics`, so the reverse would be a cycle.

Measured in the harness, a report from a live run now carries **37 fields**:

```
display = browser            <- standalone vs tab, the one thing separating the devices
viewportCss = 844x198        <- and canvas = 2532x1170, so both spaces are named
dpr = 3                      rawDpr = 3
screenAngle = 90             <- 'absent' when the API is missing, which is itself the answer
portrait = false             rotateOverlay = hidden
insetsRaw = {"top":0,"right":47,"bottom":21,"left":47}
insetsResolved = {"top":0,"right":0,"bottom":21,"left":47}
gates = none                 openGates = none
scenesRunning = Game,Hud     scenesPaused = none
gateHolding = nothing        renderer = canvas
visibility = visible
... plus the 20 run fields GameScene already provided
```

`formatReport` also says so out loud if the section is ever empty again, because
an empty STATE is now itself a fault rather than the normal outcome of crashing
outside a run.

## Step 2 — the orientation gate, answered

**What happens to scenes, timers, tweens and input when the gate goes up and
comes down 21ms later?** Scenes are paused and resumed through Phaser's scene
manager, and the gate resumes only what it paused — it tracks them in a `held`
set and skips `Boot`. Timers and tweens are not touched directly; they stop and
start with their scene. Sound is paused and resumed, inside a `try`. On the
reported path `held` was empty, so **nothing was paused and nothing was
resumed**: the events say so, and it is correct. Nothing is resumed twice: the
raise re-runs `hold()` every portrait frame but `held` is a `Set`, and the
release clears it.

**Is the "holding nothing" path exercised anywhere?** It was not, before this
session — every existing test drives the gate with `['Game', 'Hud']` or
`['Boot','Game','Hud']` running. There is a test for it now, and it is the one
that catches the defect below.

**How many readings does `portraitReadings` actually require, and can a
standalone viewport satisfy that in one frame?** `ENTER_FRAMES = 3`, and the
implementation genuinely requires three *consecutive* readings — `streak` is
reset to 0 by any landscape frame, and the gate returns early below the
threshold. It cannot rise on one frame. **The gate did not misfire.** During
boot the loader is decoding 18 MB of art and frames are slow, so three
consecutive readings is a much longer wall-clock window than the 50ms it would
be at 60fps; a launch that starts portrait and rotates into landscape satisfies
it honestly. The 21ms between raise and lower is one frame at the far end of
that, not evidence of a transient being believed too readily.

**Is `screen.orientation.angle` present and correct at launch, and can an
undefined angle throw?** `SafeArea.screenAngle()` returns `null` unless the value
is a `number`, and `housingSide` returns `null` for `null` or any non-finite
value, and `resolveInsets` returns the raw insets unchanged when the side is
`null`. **An absent or undefined angle cannot throw; it degrades to keeping both
insets, which is over-cautious rather than wrong.** This candidate is closed.
The new report records the angle as `absent` when it is missing, so the next one
will say whether it was.

**Does any layout calculation divide by a viewport dimension, or index an array
by one?** `applyResolution` clamps with `Math.max(1, ...)` on both axes and
falls back through `box?.width || innerWidth || 1`, so a zero-sized parent
cannot produce a zero. `deviceScale` clamps to `[1, 3]` and rejects non-finite
values. `viewW`/`viewH` divide *by* the device scale, never by a viewport
dimension. I found no division by a viewport dimension and no array indexed by
one.

## Step 3 — what reproduced, and what did not

A new harness scenario, `standalone`, plus a `PORTRAIT=startMs,durMs` switch
that shadows `matchMedia('(orientation: portrait)')` for a window during boot —
and deliberately not the CSS, so the stylesheet keeps answering honestly and the
real pairing is reproduced: the script believes portrait while the overlay stays
hidden.

```bash
sh tools/harness/build.sh
INSETS=0,47,21,47 ANGLE=90 PORTRAIT=1500,1200 sh tools/harness/run.sh standalone 160 844x390
```

Runs, all clean, all reaching a playable run with zero page errors:

| viewport | insets | angle | portrait window | gate | result |
|---|---|---|---|---|---|
| 844x390 | 0,47,21,47 | 90 | 1500ms +1200ms | raised 1, lowered 1 | clean |
| 844x390 | 0,47,21,47 | 90 | none | never rose | clean |
| 844x390 | 0,47,21,47 | — | 500ms +1500ms | raised 1, lowered 1 | clean |
| 844x390 | 0,47,21,47 | — | 2500ms +1200ms | raised 1, lowered 1 | clean |
| 1180x820 | none | — | none | never rose | clean |
| 1400x820 | none | — | 2000ms +1000ms | raised 1, lowered 1 | clean |

**The exception did not reproduce.** The raise-and-lower-holding-nothing path
was driven directly, at the reported viewport, with the reported insets, and the
game booted through it to a title and into a run every time.

### What did reproduce

The scenario found this, which was not what it was looking for:

```
overlay visible now: false   gate holding []   open gates portrait(3885ms holding=nothing)
```

The gate had lowered. It was holding nothing. The overlay was down. And the
`portrait` gate was **still claiming to hold input**, seconds later, for the rest
of the page's life.

`OrientationGate.sync()` called `enterGate('portrait')` on the way up and nothing
on the way down. Only `forceRelease()` ever called `leaveGate`, and that runs
only after the stuck guard has already decided something is wrong. So the claim
leaked on every ordinary raise-and-lower.

That is not cosmetic. In `StuckGuard`:

```ts
export function shouldRecover(v: StuckVerdict): boolean {
  return v.stuck && v.owner === null
}
```

and `owner` is `openGates()[0]`. **One portrait transient permanently disarmed
the stuck guard.** After it, a genuine soft lock — the exact failure the guard
was written for, after a player hit one on level 1 — could never be recovered,
because an invisible gate the player cannot see or dismiss was claiming to own
the state.

The iPhone report shows that transient on the launch that crashed. Every launch
on that device was arming this.

The fix is one line: `leaveGate('portrait', ...)` on the lowering path. Two tests
drive the state machine, and both fail without it:

```
not ok 11 - a raise and a lower leave no gate claiming to hold input
not ok 12 - a gate that raised holding nothing still lets go of the claim
```

The second is the reported shape specifically: the gate rises with only `Boot`
running, so it pauses nothing at all, and comes straight back down. The harness
asserts the same property against a real boot.

**This is not the crash.** It does not throw. It is a latent defect that turns
any *later* freeze into a permanent one, and it was found in the file step 2
pointed at.

## Step 4 — what was changed

Only what reproduced, plus the diagnostics step 1 asked for. No speculative
hardening, no `try`/`catch` around the gate, nothing that would swallow the
exception rather than fix it.

- `index.html` — `crossorigin="anonymous"` on the module script.
- `src/systems/Diagnostics.ts` — a context registry; state merged context-first
  with the run over the top; an explicit complaint if STATE is ever empty.
- `src/systems/CrashContext.ts` — new; the environment and game facts above.
- `src/main.ts` — installs the page context immediately after the error handler
  and before anything else, and the game context after the gate.
- `src/systems/OrientationGate.ts` — the missing `leaveGate`.
- `tests/orientation.test.ts` — the two regression tests.
- `tools/harness/` — the `standalone` scenario, the `PORTRAIT=` switch, and the
  error panel and crash context installed on the harness's boot path so what
  ships is what is exercised.
